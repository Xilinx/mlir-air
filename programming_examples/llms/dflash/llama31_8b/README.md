# Llama-3.1-8B-Instruct DFlash on NPU2

This example runs the Llama-3.1-8B-Instruct target and its official Z-Lab
DFlash drafter with block size 8 by default. NPU programs perform prompt prefill,
context preparation, drafting and verification. The host accepts the matching
draft prefix, commits KV state and streams the resulting tokens.

The target uses the FastFlowLM Q4NX checkpoint. The drafter body is quantized
from the pinned official BF16 checkpoint to group32 Q4NX; its learned context
projections use BF16 weights and BFP matrix arithmetic. The drafter checkpoint
was trained with block size 10. B8 and B16 are execution configurations;
B16 does not imply a checkpoint trained for sixteen positions. See the
[B16 mapping](docs/b16-megakernel.md) for its shared AIR graph and compiler
requirements.

## Run

Activate the normal MLIR-AIR environment, including XRT and a pre-23
`llvm-link` for inline attention. Install this example's Python requirements:

```bash
cd programming_examples/llms/dflash/llama31_8b
python3 -m pip install -r requirements.txt
make download
make weights
make compile
make run PROMPT="Explain speculative decoding." N_TOKENS=128
make chat
```

`make download` seeds the pinned target, drafter, tokenizer and HF BF16
verification reference. Subsequent runs can use `OFFLINE=1`. Model snapshots
use the normal Hugging Face cache. Converted weights are cached under
`~/.cache/mlir-air/dflash/llama31_8b`; compiled programs use `build/` (B8) or `build_b16/` (B16).
`DFLASH_CACHE_DIR` and `BUILD_DIR` select other locations. No research checkout
or retained experiment artifact is required.

`make run` streams a response. `make chat` prepares the model once, then
accepts independent prompts; it does not retain conversation history.
Both use NPU prefill, with a default padded capacity of 2048. Decode capacity
is 4096, and the runner checks that the prompt, output and final candidate block fit.

Pass `BLOCK_SIZE=16` to the compile/run/chat and verification/benchmark commands
to select B16. Both configurations use the same pinned resources and caches.

## Verify and benchmark

```bash
make verify
make profile
make compile-baseline
make full20                  # 4 prompts from each of 5 datasets
make full80                  # optional: 16 prompts from each dataset
```

The paired study uses the existing native `llama31_8b_q4nx` B1 decoder and
the selected DFlash loop. Both receive identical saved NPU-prefill states.
The shared frozen prompt texts are in
[`common/benchmark/prompts.json`](../common/benchmark/prompts.json): GSM8K,
MATH500, HumanEval, MBPP and the first turn of MT-Bench. Full80 means all
80 selected requests, not every request in the source datasets.

Decode throughput is timed output tokens divided by decode time, excluding
the first token generated by prefill. DFlash timing includes the initial and
incremental NPU context prepass, draft and verify calls, acceptance and host
work. Loading, prefill and KV reset are excluded. Both engines use greedy
decoding, EOS stopping and a 2048-token cap. Overall throughput is pooled
across requests; the report also records each dataset and emitted tokens per
round. The native B1 comparator uses its fixed-C4096 xclbin mode.

The B1 comparator retains the native GEMV arithmetic and its existing decoder
normalization epsilon (1e-6). The B8 target uses the checkpoint epsilon (1e-5)
and batched matrix arithmetic. Exact acceptance/KV verification therefore
uses a sequential oracle built from the same B8 target, while B1 provides the
existing upstream performance baseline.

The compile, verify, profile and Full20 LIT entries follow the other DFlash
examples. Full80 is opt-in through `dflash_full80=1`. Checkpoints and prepared
prompt states persist between nightly runs. The shared NPU is protected by
`/tmp/mlir-air-npu.lock`.

## Code and model differences

| Files | Responsibility |
|---|---|
| `model_spec.py`, `model_paths.py`, `resources.py` | Role semantics, checkpoint revisions and downloads |
| `target_config.py`, `selected_config.py` | Bind the shared B8 mapping to the two model roles |
| `batch_graph.py`, `owner_graph.py` | Entry points to the common two-owner AIR graph |
| `build_target.py`, `build_bfp_prepass.py` | Compile decoder and context-preparation programs |
| `target_weights.py`, `draft_weights.py`, `prepare_*.py` | Native weight readers, packing and input handling |
| `npu_prefill.py`, `prefill_weights.py` | Native Llama prefill with tapped hidden states and streamed weights |
| `dflash_model.py`, `target_runtime.py`, `run.py` | This model's decoders and caches for the shared runtime in `common/`, and the streaming entry point |
| `verify_loop.py`, `tests/` | Entry points for the shared state/visibility checks, sequential oracle and HF token comparison in `common/` |
| `baseline.py`, `benchmark*.py`, `paired_benchmark.py` | Native B1 comparator, frozen cohort and paired results |

The B8 implementation is in
[`common/b8_graph.py`](../common/b8_graph.py) and
[`common/b8_owners.py`](../common/b8_owners.py). Both Llama and Qwen3-8B use
two four-row residual owners, each with a separate normalized-activation
cache. Eight hidden rows of width4096 occupy64KiB, so placing all residual
state on one compute tile would leave no room for weights, staging or stack.
The projection and attention primitives are shared under `common/kernels/`.
The models compile separate target and drafter programs.

| Property | Target | Drafter |
|---|---|---|
| Layers | 32 | 5 |
| Hidden / FFN width | 4096 / 14336 | 4096 / 12288 |
| RMS epsilon | 1e-5 | 1e-6 |
| Q/K normalization | Absent | Present |
| RoPE | Llama3 scaling, factor8, theta500000 | Ordinary, theta1000000 |
| Block visibility | Causal | Bidirectional |

The target's selected layer outputs are captured at boundaries2/9/16/23/30.
Its untied LM head is shared with the drafter. EOS IDs128001/128008/128009
come from the target configuration, and mask ID128002 comes from the drafter.
The drafter's inherited Qwen EOS metadata is not used.

See [compatibility and pinned resources](docs/compatibility.md) and
[tests/nightly integration](docs/validation.md) for the upstream interfaces
and verification coverage.

## Verification scope

The model check uses AIR's two-prompt, 32-token mutual top-5 gate. It stops
comparison at the first accepted divergence; the report records the actual
visited prefix. Separate DFlash checks cover repeated outputs, causal and
bidirectional visibility, KV injection, acceptance and committed KV against
a sequential oracle using the same B8 arithmetic. See
[CI and validation](docs/validation.md) for the commands and gates.
