    LLMs and VLAs on NPU¶

    End-to-end inference of decoder-only LLMs and vision-language-action (VLA) policies on the AMD NPU2 via MLIR-AIR, with bf16 and 4-bit (Q4NX, Q4_0) weights. Models with an FLM link reimplement AMD NPU LLM designs originally developed by the FastFlowLM team, using the higher-level abstractions of the MLIR-AIR dialect; the link points to the original FastFlowLM code. Coverage and performance below are refreshed nightly. Per-model details and source are in programming_examples/llms/.

    Accuracy (the decode table's KLD, GSM8K and MMLU; the prefill table's KLD). The NPU is compared with the same model on the CPU (PyTorch): on wikitext-2 the way llama.cpp's llama-perplexity --kl-divergence does, and on benchmark questions. Measured offline. The NPU gives the same accuracy on every NPU2 machine, so a row whose accuracy was measured on other hardware names it under Hardware. Hover over a number for its details.

    • KLD: KL divergence of the NPU's next-token distribution from the CPU's with the same weights (4-bit weights dequantized on the CPU); 0 means identical. It measures the NPU implementation alone.
    • GSM8K / MMLU: % correct, NPU / original bf16 checkpoint on the CPU, on the same questions (GSM8K 100, MMLU 570). For 4-bit models this includes the cost of the 4-bit weights.

    Prefill latency vs prefill length (TTFT, ms)¶

    Time to first token at increasing prefill length. A model with a fused prefill is timed on a prompt of exactly that many tokens, one build serving every length. A per-op prefill pads the prompt to the length its ELFs were built for, so each of its columns is a separate build and TTFT tracks that length rather than the number of real prompt tokens.

    Speculative decoding¶

    A draft model proposes a block of tokens and the target model verifies the block in one pass. Target only is the same target model decoding one token per pass. Both decode the same 20 prompts, 4 from each of gsm8k, math500, humaneval, mbpp, mt-bench, greedy, up to 2048 new tokens, prefill excluded. Prompts are 20–305 tokens. Throughput is each engine's total generated tokens divided by its total decode time over the requests in the row. The two engines use different matrix arithmetic (single-token GEMV vs batched verification), so their greedy outputs diverge and the generated token counts differ.

    Vision-Language-Action policies¶

    Not autoregressive: these emit one action chunk per observation rather than a token stream, so there is no decode throughput and no context to sweep. Action chunk is the latency to the model's first usable output. Prefix is the token count the backbone attends over.
